**🟢 変わらず動きやすいもの**
- 言語サポート、テーマ、リンター、フォーマッタのように、安定 API だけを使う拡張。
- フォーク側には拡張エコシステムを使い続けたい理由があり、土台の VS Code も定期的に取り込むので、ここは大きくは崩れにくいはずです。

**🟡 版の差でじわじわずれるもの**
- **`engines.vscode` の差**：新しい VS Code を要求する拡張は、土台が古いフォークに入りません。このセッションで見た範囲では、Cursor 3.27.22 の土台は 1.128.0、本家は 1.144.0 で、差は 16 マイナー版です。拡張側は、要求する版を低く抑え続けるか、フォークを切り捨てるかを迫られます。
- **配布先の差**：フォークは Microsoft の Marketplace を正式には使えず、Open VSX などに分かれます。Microsoft 製の一部の拡張（Pylance、Remote 系など）は、ライセンス上もともと本家専用です。

**🔴 崩れやすいもの（今回まさに起きている部分）**
- **AI 統合**：VS Code はチャット API、MCP、`contributes.chatSkills` などを本体に組み込み続けています。一方フォークは独自の AI を持っています。Codebook でもスキルの登録方法は、VS Code では `chatSkills`、Cursor では `~/.cursor/skills` へのセットアップ、と分かれています。
- **workbench の改造**：Cursor はセカンダリサイドバーを自分用に確保していて、Codebook の Learning summary は「Move Learning Summary…」で回避しています。さらに今回の試行では Agent チャットが編集グループ扱いになっていて、Codebook が Application ペインを動かしたときに、グループ番号のずれから配置ガードが拒否しました（Cursor の Codebook.log、20:37:42 の `placement-refused`）。レイアウトやフォーカスに依存する拡張ほど、フォークごとに個別対応が要ります。
- **proposed API や、仕様にないタイミングへの依存**：いちばん脆い部分です。

**📌 作る側の構え**
- 「VS Code 拡張だからどこでも動く」とは考えず、ホストを一つずつ別のターゲットとして扱う。
- 使えるかどうかは実際に確かめ、使えない機能はそう伝える。
- 動作はホストごとに実機で確かめる。

AGENTS.md の「あるホストの証拠は別のホストを検証しない」というルールは、まさにこの前提に立っています。

📝 訂正ありがとうございます。Devin Desktop は 2026-06-02 に Windsurf から改名されたものですね（Cognition の公式 FAQ で確認しました）。

**🧱 構造の見立ては同意です**
- 2023 年ごろの VS Code はほぼ素の IDE で、AI はタブ補完程度でした。だからフォークして AI を足すのは比較的楽でした。
- 今は AI が本体の奥まで入っています。フォークは自分の AI と衝突する部分を避けながら、Electron や Chromium の更新を含む土台だけを取り込む必要があり、差分が膨らむほど作業は重くなります。
- 今回の試行でも、Cursor の土台は 1.128.0、本家は 1.144.0 で、差は 16 版ありました。

**🤔 意図的な妨害か：私の見方**
主目的は「フォーク潰し」というより、Cursor と競争するための製品戦略だと思います。AI の体験を速く良くするには本体に深く組み込むのが早道で、フォークが苦しくなるのはその副作用です。ただ、その副作用を Microsoft が嫌がっていないのも確かだと思います。

ビジネス側が手間をかけずに守れる所はしっかり守っている、という証拠もあります。
- Marketplace の規約で、Microsoft 製品以外での利用を禁止している。
- Pylance や Remote 系はプロプライエタリ（非オープンソース）。
- 2025 年 4 月に C/C++ 拡張が Cursor などの非公式ビルドで動かないよう、実行環境を確認するようになった（確認済み）。

逆に、オープンソース側の振る舞いもはっきりあります。
- Copilot Chat 拡張を MIT ライセンスで公開し、AI 機能をオープンソースの本体へ移す方針を打ち出した（2025 年）。AI のコードを隠しているわけではありません。
- MCP という他社発の標準を採用した。
- 自前のモデルを持ち込める API や、チャット参加者 API を公開している。

**🔌 汎用プロトコルの案について**
ここが面白い点だと思います。ACP のような汎用プロトコルを挟むと、VS Code はどのエージェントでも載せられるハブになります。ただそれは、フォークを楽にするというより、**フォークする理由自体をなくす**方向に効きます。

Cursor や Devin Desktop がフォークするのは、拡張 API やプロトコルでは手に入らないホスト側の体験（補完、インライン編集、エージェント中心のレイアウト）を自分で握りたいからです。プロトコルはそこを渡してくれません。

なので Microsoft の合理的な戦略は「あらゆるエージェントが動くオープンなハブになり、初期設定は Copilot」で、強い妨害は要りません。実際、VS Code の GitHub には ACP 対応の要望 Issue（#265496）があり、Zed と JetBrains は ACP を支持しています。この Issue の現状は確認していません。

**🏢 チームはビジネス寄りか、オープンソース寄りか**
両方だと思います。それは 2015 年からの構造そのものです。
- 「Code - OSS」は MIT ライセンスで、GitHub 上で開発され、計画も公開されています。開発文化はオープンソースです。
- 「Visual Studio Code」という製品（ライセンス、Marketplace、テレメトリ、初期設定）は、Copilot を収益源とする Microsoft と GitHub のビジネスの中にあります。

なので「コードはオープンソース、配布と初期設定はビジネス」と読むのが一番実態に近いと思います。内部で何を考えているかは、外からは分かりません。

Codebook にとっては、ホストごとの違いは今後も広がる前提で、ホストごとに実機で確かめる今のやり方が合っています。

**🔓 「オープンだけど自由ではない」について**
- 実はコード自体は MIT ライセンスで、ライセンス上はオープンソースでもあり自由なソフトウェアでもあります。自由を制限しているのはコードではなく、その周りのサービスです。
  - 拡張：自分でビルドした版は Microsoft の Marketplace を規約上使えず、Pylance などのプロプライエタリ（非オープンソース）拡張も使えません。ただし Open VSX の拡張は使えます（VSCodium はこの形です）。なので「拡張が一切使えない」わけではありません。
  - Copilot：GitHub へのログインが前提です。私の知る限り、制限付きの無料枠（Copilot Free）はあります。
- この構造は 2015 年から明示されていて、Chromium と Chrome の関係と同じです。開発者はそれを承知で入社し、オープンソースの本体を作る仕事として納得している人が多いだろうと思います。内心までは分かりません。
- 同じ構図は業界全体にあります。Zed も 2024 年にコードを GPL などで公開していますが、ホスト型の AI 機能は有料プランです。「コードは自由、サービスは課金」は今の開発ツールの標準的な稼ぎ方で、GPL でもこれは防げません（だから AGPL が生まれました）。

**🧑‍💻 Zed と Atom（zed.dev のチームページで確認）**
- Nathan Sobo（CEO）は 2011 年に Atom を作るために GitHub へ入り、2018 年まで Atom チームを率いました。
- Max Brunsfeld は 2013 年に Atom チームに加わり、Tree-sitter を作った人です。Antonio Scandurra は 2014 年に加わりました。
- Zed の土台は 2019 年末ごろから作られ始め、会社は 2021 年に創業しています。Atom の終了発表（2022 年）より前です。
- 彼らが公に語っている理由は技術面です。Web 技術の Atom では性能の天井を越えられないので、Rust と GPU 描画（GPUI）で作り直す。Atom の Teletype で試した共同編集を本格的にやる。
- 「Microsoft の文化が合わなかった」と本人たちが言っているのは見たことがありません。ここは推測になります。構造的には、2018 年の買収で同じ会社が VS Code を持つことになり、Atom に未来がなくなった、という方が説明として自然だと思います。

いいえ、VS Code は Atom のフォークではありません 🙅 共通しているのはエディタのコードではなく、実行基盤の Electron だけです。

- **🧩 エディタ部分**：Microsoft 自前の **Monaco Editor** から来ています。Erich Gamma（Eclipse や「デザインパターン」本で知られる人）がチューリッヒのチームで作ったブラウザ向けエディタで、2013 年ごろの Azure 上の Web エディタ（「Visual Studio Online "Monaco"」）などで使われていました。これを TypeScript で発展させたのが VS Code です。
- **🖥️ 実行基盤**：2015 年の発表時、VS Code は GitHub が Atom のために作ったデスクトップ用の殻「Atom Shell」を採用しました。これはちょうど同じ年に「Electron」へ改名されています。
- **⚖️ 違い**：Atom は Electron の上に CoffeeScript/JS で独自のエディタを作り、VS Code は Electron の上に Monaco を載せました。家の基礎は同じで、建物は別、という関係です。

混同されやすいのは、初期の VS Code が「Atom Shell で動く」と紹介されていたからだと思います。前の話とつなげると、Microsoft は Atom のコードではなく、GitHub が Atom のために作った土台を借りて VS Code を作りました。その後 Microsoft 自身も Electron に大きく貢献していきます。

分かります。「A hackable text editor for the 21st Century」という宣伝文句で、紹介動画もかなり凝っていましたよね 🎬 ただ、振り返るとその「hackable」が実用性の弱さの原因そのものだったと思います。

**🔧 拡張がすぐ壊れた理由**
- Atom は DOM も内部オブジェクトも拡張にほぼ丸ごと見せていました。何でもいじれる代わりに、拡張が内部実装に依存してしまい、本体が更新されるたびに壊れました。
- 大きなファイルで重くなるのも、この全部見せる構造と無縁ではありません。
- CoffeeScript も、ES2015 の登場で存在意義が薄れて、エコシステムごと古びていきました。

**🏗️ VS Code が逆を選んだ点**
- 拡張は別プロセス（Extension Host）で動かし、DOM には触らせず、安定した `vscode` API だけを渡しました。自由度を削った分、速くて壊れにくくなりました。
- 前の話とつながりますが、Cursor がフォークした理由もここにあります。この API ではエディタの UI そのものを作り変えられないからです。

**🧠 IDE になれたのはプロトコルのおかげ**
- Microsoft は 2016 年に LSP（Language Server Protocol）を出し、デバッグには DAP（Debug Adapter Protocol）を用意しました。言語の知能とデバッガを、エディタ本体ではなくプロトコルの向こう側に置いた設計です。これで VS Code は「エディタの軽さで IDE の機能」に届きました。
- Atom も 2017 年に Facebook と Atom-IDE を出しましたが、遅すぎました。Atom ベースだった Facebook の Nuclide も 2018 年に終了しています。

JetBrains の深いリファクタリングやインデックスにはまだ及ばない言語もありますが、「無料で、十分に IDE」という位置を取れたのは LSP と DAP の功績が大きいと思います。ちなみに Codebook のネイティブデバッガ連携も、まさにこの DAP の上に乗っています 🙂
